# Restricted Loop G6 research build

This branch builds the existing Loop application target with a restricted entrypoint. It reuses LoopKitUI's glucose chart and CGMBLEKit's G6 setup/settings screens. Original Loop therapy, pump onboarding, services, watch and extension entrypoints are excluded from this target. It is not a general treatment build of Loop.

The independent Dexcom G6 phone app and t:slim Basal-IQ treatment must remain operating. The research variant has no pump manager, simulated pump, pump transport, dosing UI, or treatment settings. Its separate bundle identifier is `org.projectlive.loop.g6research`, with empty application entitlements and private local storage.

## Build and verification

Open `LoopWorkspace.xcworkspace` and select `LoopG6Research`. Every reached CGM/Share Swift target must retain `LIVE_READ_ONLY`; `Scripts/verify_g6_research.py` checks target overrides. The branch's default `LoopWorkspace` scheme is restricted as well, to avoid accidentally selecting the full treatment build.

```sh
python3 Scripts/verify_g6_research.py --app /path/to/Loop.app
python3 Scripts/test_g6_notification_routing.py
swiftc Loop/Research/ResearchPolicy.swift Loop/Research/ResearchObservation.swift Loop/Research/Tests/main.swift -o /tmp/live-g6-policy-tests
/tmp/live-g6-policy-tests
xcodebuild -workspace LoopWorkspace.xcworkspace -scheme LoopG6Research -configuration Debug \
  -destination 'platform=iOS Simulator,id=YOUR_SIMULATOR_ID' -jobs 2 \
  -parallel-testing-enabled NO -onlyUsePackageVersionsFromResolvedFile \
  -disableAutomaticPackageResolution CODE_SIGNING_ALLOWED=YES CODE_SIGN_IDENTITY=- test
```

The host-side Swift test emits a **synthetic fixture of the production observation format**, not a sensor reading. Never import that fixture as captured health evidence. Native tests cover empty history, a single observation, backfill rendering, and forbidden manager identifiers. Existing upstream therapy tests are not selected by this restricted scheme.

Application characteristic writes fail closed at both G6 write entrypoints; passive mode cannot be disabled and expiry reads cannot be enabled. Cloud HTTP, credential restoration/writes and the upstream simulator glucose generator are excluded. The app only considers peripherals returned by iOS as already system-connected: no discovery scan, known-UUID reconnect or new-device fallback. After collection consent, foreground lookup checks the existing system connection once per second automatically. Receiving a reading does not stop collection. Lookup pauses when the app becomes inactive and resumes when it becomes active; an explicit owner pause persists across activation/relaunch and must be resumed by the owner. Revocation or storage failure stops collection. The polling callback performs lookup only, without rebuilding charts and journals every second. It cannot queue a duplicate connection while a connection request is pending. The in-memory Connection diagnostics v1 panel exposes only fixed Bluetooth/stage labels, counts and flags; it contains no transmitter identifiers, glucose values, packet bytes or health timestamps. These counters distinguish lookup, matching, authentication, control notifications and the observed-time prerequisite; counts are not proof of valid glucose readings. On joining an existing connection, the research observer subscribes only to control notifications. Optional authentication subscriptions are omitted so their failure cannot interrupt a working control subscription. It does not wait for an authentication broadcast that may have already passed, and never sends an authentication request. An already-enabled notification is not requested again. Missing transmitter-time evidence still prevents constructing a glucose observation; no timestamp is invented. BLE service discovery and notification subscription still use operating-system protocol operations; absence of application commands does not establish absence of every possible pairing prompt or impact. Local synthetic recovery tests do not establish sustained hardware coexistence or background continuity. Upstream matching uses the last two transmitter-ID characters and does not independently prove the full transmitter identity.

## Local observations and export

Collection requires explicit consent before G6 configuration/restoration. Glucose observations retain measurement and receipt timestamps and upstream quality, including display-only/user-entered/condition/trend. The upstream manager filters unreliable packets and clamps glucose to its supported range; the research app preserves the resulting quality condition and does not describe this as raw sensor chemistry. No simulator sample generator runs.

Private append-only daily journals retain seven UTC calendar days. Retention is checked at opening, collection and export. Export separately requires owner consent and creates `Documents/LIVE/observations-v1.jsonl` for an owner-initiated USB/Finder copy. Export is disabled when reopening the app or deleting the local G6 observer. Files use complete protection until first device unlock and are excluded from backup. No cloud upload or network server is introduced.

The versioned format is `project-live.cgm-observation`, version 1, source `loop.dexcom-g6`, source version `loop-g6-passive-v1`. IDs are stable SHA-256 pseudonyms of source and sample sync identifier; no raw transmitter ID is exported. Glucose records remain private health data. This build is strictly observational and is not validation of real-world insulin control.


## Untimed packet evidence

A recognized glucose opcode is not proof of a valid reading. The diagnostic panel separately counts successfully decoded packets, invalid packets, missing-clock packets and bounded-buffer overflow. The existing decoder checks message shape and CRC before retaining a packet. Without an observed transmitter-time message, its device-relative timestamp does not establish absolute measurement time. Receipt time is not substituted.

Valid but untimed packets and later clock-reference packets are retained separately in protected, backup-excluded Application Support storage under private versioned schemas `project-live.cgm-untimed-packet` and `project-live.cgm-clock-reference`. Records preserve the original packet bytes, captured receipt wall/monotonic time, device uptime, sequence and quality fields. `event_at` is explicitly null. SHA-256 identity uses local stream identity and original packet content, without transmitter serials. Within-stream duplicates retain the first receipt; a new stream after restart makes no cross-restart identity claim. Journals prune to seven UTC calendar days on opening/append. In-memory buffers retain 24 records each and report overflow, so complete capture is not promised.

The readout labels untimed packet values and unknown currentness. These records never enter the timed chart, `observations-v1.jsonl` export or Bayesian replay; actual export exclusion is exercised by native tests. A later clock packet does not rewrite or automatically promote earlier evidence. This preserves original evidence separately from interpretations under Project LIVE [ADR 0003](https://github.com/thebookoftheway3/project-live/blob/main/docs/decisions/0003-observation-payload-snapshots.md). It does not add a new remote acquisition path, clock query, authentication request or treatment command.


## Background observation and recovery

The existing `bluetooth-central` background mode is retained. The observer registers for iOS connection events matching the G6 services. Each connected-event callback performs the same fresh system-connected lookup and configured-name check; event hints never directly authorize a connection. OS-restored handles wait for consent activation and Bluetooth power, then must also appear in a fresh system-connected query before being rebound. The observer starts disabled until the app restores collection consent. Pause/revocation disables event registration and local observation. No known-UUID reconnect, new scanning, pairing, active authentication, network fallback or treatment control is added.

A background launch explicitly recreates the consented journal/manager without waiting for a foreground view. Bluetooth callbacks write observations with their existing provenance/quality rules while chart rendering remains foreground-only. Configuration invalidation is queued asynchronously: a Bluetooth callback must not wait behind discovery that requires that same callback queue. Discovery begins after delegate attachment. This prevents a queue stall; it does not prove the cause of every missing physical packet.

Unsolicited value notifications now reach the passive decoder even while service discovery or subscription acknowledgement is pending. Expected command responses and registered macros retain their routing priority. Failed value callbacks are not forwarded because their cached value may be stale. The host regression executes the actual production callback against synthetic Bluetooth stand-ins, including notifications arriving during pending setup, matched/unmatched replies, error callbacks and unlocked delegate delivery. Reintroducing the old pending-operation drop or stale-error forwarding must fail. This harness tests callback logic, not CoreBluetooth radio behaviour.

After a disconnect or failed attachment, all event and foreground lookup paths observe the pinned upstream's two-second shutdown interval, using monotonic time. A delayed dispatch replaces immediate reconnect without blocking the callback queue. Native tests exercise the interval boundary; source checks catch bypassing the common gate or scheduling an immediate retry. A queued callback still must pass consent, Bluetooth power and fresh system-connected checks. These corrections do not establish reliable background capture or coexistence on a physical device; the PR remains held for that evidence.

The alternative of repeated foreground timers cannot wake a suspended app. Unrestricted reconnection would broaden the acquisition boundary, so it remains excluded. This change follows existing adapter separation and evidence rules in Project LIVE ADRs [0001](https://github.com/thebookoftheway3/project-live/blob/main/docs/decisions/0001-modular-monolith-first.md) and [0002](https://github.com/thebookoftheway3/project-live/blob/main/docs/decisions/0002-lightweight-assurance-traceability.md). The background implementation is based on Apple's [connection event API](https://developer.apple.com/documentation/corebluetooth/cbcentralmanager/registerforconnectionevents(options:)) and [state restoration guidance](https://developer.apple.com/documentation/technotes/tn3115-bluetooth-state-restoration-app-relaunch-rules). Delivery of matching G6 events while suspended requires hardware evidence; simulator tests cannot establish it. Force-quitting this variant, disabling Bluetooth or a restart before the first unlock can prevent recovery. This build does not use AccessorySetupKit or reconfigure the existing accessory.

A separate protected, backup-excluded `Library/Application Support/G6ResearchStatus/status-v1.json` snapshot contains only fixed-schema operational counters, observer state and the sanitized Bluetooth diagnostics. It contains no glucose values, transmitter identifiers, raw packets or observation timestamps. `backgroundTimedSamples` counts successfully handled samples in background callbacks; `journalCount` permits checking whether the stored set grew. Counters reset with the process and are not clinical evidence or a completeness guarantee. Reading this specific status file locally does not enable the observation export or authorize uploading either file. Optional status-write failure does not discard a stored observation; observation-storage failure still stops collection.
